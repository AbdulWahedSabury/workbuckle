# Project Rules

## Tech Stack
- Next.js 16 (App Router) + React 19 + TypeScript (Strict Mode)
- Tailwind CSS v4 + shadcn-style primitives in `components/ui/`
- Prisma 7 ORM (`@prisma/adapter-pg`) + PostgreSQL
- Auth.js (`next-auth` v5), `next-intl`, Zod, React Hook Form, TanStack Query

## Project Layout
- `app/(site)/` public site, `app/(admin)/` admin panel, `app/api/` route handlers
- `lib/prisma.ts` is the single Prisma client (global singleton). Import `prisma` from `@/lib/prisma`; never call `new PrismaClient()` elsewhere.
- `lib/generated/prisma/` is generated by `prisma generate`. Never edit, refactor, or lint-fix it by hand.
- `lib/<domain>/` holds data access per domain (`lib/jobs/public-jobs.ts`, `lib/admin/queries.ts`, `lib/faqs/public-faqs.ts`, ...)
- `lib/admin/actions/` and `lib/jobs/actions.ts` hold Server Actions (`"use server"`)
- `schemas/` Zod schemas · `types/` shared types · `constants/` static content · `utils/` server utilities (mailer, cors)

## Architecture & Boundaries
1. **Data layer:** All Prisma queries live in `lib/<domain>/` query or action modules. Server Components and Server Actions fetch data by calling those functions, never by querying Prisma inline in `app/` or `components/`. Route handlers in `app/api/` should follow the same rule where practical.
2. **Server vs. Client:** Components are Server Components by default. Add `"use client"` only at the leaf level when state, effects, browser APIs, or interactivity are required.
3. **Mutations:** Prefer Server Actions over API routes. Use route handlers only where they're actually needed (streaming, auth callbacks, external consumers).
4. **Validation:** Validate all incoming runtime data at the Server Action / API boundary with Zod schemas from `schemas/`.

## Coding Standards

### TypeScript
- No `any`, ever. Use precise types, generics, or `unknown` + narrowing. Fix existing implicit `any` and add missing return types on exported functions.
- For database objects, use Prisma's generated types (model types, `Prisma.<Model>GetPayload<...>` for `include`/`select` shapes).

### Functions & Modules
- Functions should be single-purpose and aim for under ~40 lines. Splitting a large function or component is a structural change, so propose it first rather than doing it as part of a routine cleanup.

### Tailwind CSS
- Group classes logically: Layout → Flex/Grid → Spacing → Sizing → Typography → Colors → Interactive/Hover states.
- Remove duplicate or conflicting classes. Use `cn()` from `lib/utils.ts` (`clsx` + `tailwind-merge`) when concatenating dynamic classes.

### Prisma
- Watch for N+1 queries. Use `include` / `select` to fetch only the needed fields, and batch with `in` filters or `Promise.all` instead of querying in loops.

## Clean-up & Refactoring Protocol
When asked to clean or refactor a file/folder, follow this loop:
1. **Analyze:** Read the target and its local dependencies. Check types.
2. **Plan:** Present a bulleted summary of proposed changes (dead code, type fixes, Tailwind cleanup, ...). Wait for approval if any change is structural.
3. **Execute:** Rewrite the code safely, keeping it modular and readable.
4. **Verify:** Run typecheck and lint after *every* change. Don't assume it works because it looks right.

## Commands
- Dev server: `npm run dev`
- Typecheck: `npx tsc --noEmit`
- Lint: `npx eslint .`
- Prisma validate / format (schema only): `npx prisma validate`, `npx prisma format`
- Prisma Studio: `npx prisma studio`

## ⚠️ Guardrails (Do NOT Break)
- **No functional regressions:** Do not remove or alter business logic, feature behavior, or API endpoints unless explicitly instructed.
- **Do not touch DB data:** Ask before running `prisma db push`, `prisma migrate dev` (`npm run db:migrate`), `prisma migrate deploy`, seed scripts (`npm run seed:fake`, `admin:create`, `settings:update`), or anything else that alters schema or data.
- **Never touch environment files:** Leave `.env` / `.env.local` completely alone.
